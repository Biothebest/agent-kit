# Selective working contract and continuation

Translate a natural request into an executable agreement without making the user write a specification. Preserve the entire requested outcome. Use concise ordinary language; strict controlled English and visual formats remain opt-in.

Revision: selective-contract-20261003-1. Project coordinators and domain owners retain routing, permissions, execution and verification authority; this skill supplies only the missing task contract or continuation delta.

## Select the smallest useful mode

- **Direct answer:** one fact, access check, yes/no answer, or similarly self-contained request. Do the necessary check and return the requested format. No contract headings, handoff, extra artifact, or planning ceremony.
- **Existing complete packet:** execute it. Do not rewrite a supplied task contract, independent review assignment, checkpoint, or structured worker brief into a second framework.
- **Multi-step work:** establish the compact working contract below when unclear references, coupled steps, meaningful boundaries, or acceptance decisions could change the result.
- **Resume or handoff:** use the continuation delta. A short continuation request can still require this mode; sentence length is not task complexity.

Do not invoke every explanation skill. Select only a medium or domain skill whose trigger actually matches.

## Establish the working contract

Resolve these questions from the request, conversation, current sources and existing task state. Keep them in the existing plan or brief; do not automatically create a document or print an internal checklist.

1. **Goal:** What observable outcome did the user request? Preserve every named item. Replace ambiguous “this,” “these,” and relative history references with the exact source, artifact or request range. State a material interpretation briefly. Do not manufacture missing history.
2. **Sources and starting state:** Which files, versions, receipts and decisions establish the baseline? Distinguish current implementation, accepted target, historical observations, and assumptions. A previous answer is a claim to check, not execution evidence.
3. **Scope and boundaries:** What can change, what stays unchanged, and what approval is required? Preserve excluded formats, default settings, tenant/identity qualifiers, exact counts and external-action gates. A scope summary cannot grant permission or silently reduce the deliverable.
4. **Decisions and next action:** Identify the smallest ordered path to the outcome and any decision that changes it. Resolve tool- or repository-provided facts yourself. Ask only for an unreachable material choice; do all independent authorized work while it is blocked.
5. **Artifact and acceptance:** Name the actual deliverable and the behavior that proves it works. Apply the domain owner's real-surface verification. Separate local, independent-agent, hosted/provider and human-comprehension evidence. A format pilot is not a full-workflow performance result.

For an ordinary multi-step task, a sentence naming outcome and boundary plus the existing task list is usually sufficient. Do not repeat an entire project constitution or turn every answer into five headings. Proceed with execution in the same turn; the contract is not the deliverable unless the user asked for planning.

## Continue without replaying the whole conversation

When work is genuinely handed off, interrupted, or blocked, add one compact delta to the existing report, checkpoint or final response:

- **Goal:** the unchanged requested outcome; link a larger accepted contract when needed.
- **State:** completed artifacts and their current status. Distinguish installed, exercised, independently checked and released.
- **Evidence:** exact artifact paths and focused receipts, with revision or digest where already available. Include the source version and decisive result; never just “tests pass.”
- **Open:** every unfinished acceptance item, unresolved choice and blocker. Name the missing prerequisite and who or what can clear it. `UNPROVEN` is not success.
- **Next:** one smallest authorized, executable action, with its input/path/command when known and the expected result. State the stop condition for that action. Include owned process/worktree state only if it matters to safe continuation.

Use an existing schema's equivalent fields instead of adding duplicate headings or competing state files. A completed one-turn answer needs no empty handoff. Do not stop actionable work just to emit a handoff.

On resumption, read the named current artifacts first. Check whether their revisions, evidence or approvals have changed. Reuse still-valid work; re-run only invalidated or missing checks. If a prerequisite is now satisfied, continue from it rather than repeating the old blocked verdict. If evidence is stale, preserve the goal and invalidate only affected conclusions. Never clear a gate by blessing unexplained changes.

## Verification and improvement

Before delivery, compare the actual result against the original requested items, not merely the rewritten contract. Check that no condition, refusal, optional action or evidence limitation disappeared during compression. Make the next step concrete enough that another agent can start without guessing the environment or reconstructing prior chat.

Improve from observed defects: identify the failed outcome, correct its narrow cause in the owning artifact, exercise that path, and update the existing owner only when its contract was wrong or incomplete. Do not create another skill or new policy for every awkward sentence. More structure is useful only when it removes ambiguity, prevents a false completion claim, or carries necessary state.

## Output

Return the requested answer or artifact first, then only the evidence, limitations and continuation information needed for this task. Respect exact output formats. Report a recommendation as a recommendation and an unmeasured benefit as an inference; do not claim faster agents, better comprehension, or improved continuation without a matched observation.
